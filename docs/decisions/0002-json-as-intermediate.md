# 0002 · 分镜 JSON 是单一事实来源，不做 HTML 中间层

- 状态：已接受
- 日期：2026-10-04
- 决策者：项目作者

## 背景

要把一个目录变成视频，中间需要一层表示。作者提问：

> 「是应该先把这个目录整体搞成一个 HTML 再做视频，还是说用什么形式会比较实际一点？」

## 决策

**中间表示是「JSON 分镜 + 素材目录」，不是 HTML。**

- `foldercast.json` —— 讲什么、按什么顺序、引用哪些素材
- `assets/` —— 重活产物（缩略图、PDF 转图、视频关键帧、代码高亮图）

**不做「先渲染成 HTML 页面、再转成视频」的两段式管线。**

## 理由

### 1. Remotion 本身就是 HTML 渲染器

Remotion 的工作方式就是用无头浏览器打开 React 组件渲染出的 HTML，**逐帧截图**再编码。

所以「先做 HTML 再转视频」实际是：

```
数据 → HTML → 截图 → 视频        （所谓"HTML 中间层"）
数据 → React/HTML → 截图 → 视频   （Remotion，本来就是这样）
```

额外的一层 HTML **不带来任何新能力**，只带来：渲染两遍、动效写两遍、时序在两处维护、样式两套、调试跨阶段。

### 2. 浏览器预览已经免费

自建 HTML 层的唯一实质收益是「能在浏览器里预览」。而 Remotion Studio 已经提供实时预览、逐帧检查、时间轴拖动。`lecture-videos` 的工作流第 2 步就是 `npx remotion studio`。

### 3. JSON 承担的是「数据」职责，不是「渲染」职责

需要中间层的原因是**素材与叙述的分离**：

- 重物（PDF 转图、视频抽帧、语法高亮）不能塞进 JSON → 放 `assets/`
- 叙述与顺序是创作产物，需要人可读可改 → 放 JSON

这个分工与 HTML 无关。HTML 解决的是「怎么显示」，而我们的中间层要解决的是「讲什么」。

### 4. 确定性要求

同一份分镜渲染两次必须逐帧一致（见 [SYSTEM-DESIGN.md](../SYSTEM-DESIGN.md) 非功能性要求）。多一层 HTML 生成意味着多一处可能引入不确定性的地方。

## 后果

**正面**：
- 单层渲染管线，动效与时序只有一处定义
- 分镜可被人和模型直接编辑，改动不需要经过渲染层
- 渲染确定性强

**负面**：
- 没有「在浏览器里滚动的静态页面」这种产物形态
- 非 Remotion 的渲染后端（如纯 ffmpeg）需要自己实现 HTML/CSS 的等价能力

**对负面的回应**：静态页面形态已明确列为非目标（见 [PRODUCT.md](../PRODUCT.md) 非目标）。若将来确需「目录摘要网页」，那应该是 M1 分析器的**副产物**（结构树 + 文件卡片），而不是视频管线的必经阶段。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 目录 → HTML → 无头浏览器录屏 | 动效需在 HTML 层用 CSS/JS 实现，与 Remotion 的帧驱动模型冲突；渲染时间不可控 |
| 目录 → Markdown → 逐页截图 | 版式能力弱，无法做结构树/图片墙/视频片段等场景 |
| 目录 → PPTX → 转视频 | 依赖 LibreOffice，启动慢；且版式受 PPT 模型限制，做不了精细动效 |
| 纯 ffmpeg 逐帧合成（无浏览器） | 本机 ffmpeg 缺 libass/freetype，文本渲染能力受限；复杂版式需手写布局引擎 |
