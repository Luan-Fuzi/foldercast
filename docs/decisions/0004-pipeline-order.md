# 0004 · 管线顺序固定为「文案 → 视频 → 配音」

- 状态：已接受
- 日期：2026-10-04
- 决策者：项目作者

## 背景

三步管线有三种可能的排列。用户明确要求：

> 「我们做第一版 MVP 的话，不要分 publish 和 personal，就按最简单的流程来：先生成文案，再做视频，最后做配音。」

同时用户此前的 `lecture-videos` 采用的是「配音 → 预览 → 渲染」，即配音在画面之前。

## 决策

**固定顺序：① 文案 → ② 视频 → ③ 配音。**

并且**取消**此前设想的 `quick` / `publish` 双模式，收敛为单一流程。

## 理由

### 1. 创作与渲染分离

| 步骤 | 性质 | 迭代频率 | 外部依赖 | 成本 |
|---|---|---|---|---|
| ① 文案 | 创作 | 高 | 模型 API | 低（文本） |
| ② 视频 | 渲染 | 最高 | 无 | 零 |
| ③ 配音 | 渲染 | 低 | TTS API + 网络 | 有配额成本 |

把唯一有成本和外部依赖的步骤放最后，意味着一整天的画面迭代**不消耗任何 TTS 配额**。

### 2. 画面迭代不能被音频锁死

若先配音，场景时长由音频固定，想调版式就得重配音。先出静音版则版式自由。

### 3. 换音色是高频操作

「换个音色听听」是很自然的诉求。配音在最后，换音色只需重跑第三步，画面完全不动。

### 4. 双模式是过早优化

`quick`（静音、纯视觉）/ `publish`（完整讲稿 + TTS）的区分，在 MVP 阶段会让每个场景组件都要处理两种密度。等真实使用反馈出来再切，成本更低。

## 后果

**正面**：
- 每一步可独立跳过与重跑（见 [SPEC-pipeline.md](../specs/SPEC-pipeline.md#可重跑边界)）
- TTS 成本可控
- 实现顺序与管线顺序一致，风险从左到右递增（分析器无外部依赖，配音有）

**负面 —— 必须正视**：

**画面时长只能用预估。** 阶段②渲染时还不知道真实音频时长，场景时长必须按字数估算。中文按约 4.3 字/秒估算，实际偏差可达 30%。

**因此引入一个必要性：两遍渲染。**

| 遍次 | 时机 | 时长来源 | 用途 |
|---|---|---|---|
| 第一遍 | 阶段② | 按字数预估 | 调画面（快，静音） |
| 第二遍 | 阶段③之后 | `ffprobe` 实测 | 出成片（准，带配音） |

这不是浪费，是**设计的一部分**。它同时带来一个好处：第一遍渲染可以极快（可降分辨率、降帧率），因为它只用于看版式。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 文案 → 配音 → 视频 | 改稿必须重跑 TTS 才能看画面；版式被音频时长锁死 |
| 视频 → 文案 → 配音 | 没有文案就没有素材引用，画面无从生成 |
| 保留 quick/publish 双模式 | 过早优化，让每个场景组件承担两种密度的复杂度 |
| 文案 → 配音 → 视频 → 重新配音 | 等价于本方案，但把 TTS 成本提前了 |
