# 0005 · 版式多样化与画面密度：场景自主选择、excerpt 密度门与 Markdown 渲染

日期：2026-10-08　状态：已实施（WP1–WP3 落地，自举片按新契约重渲验收）　关联：0001（程序不替模型干活）、0004（两阶段创作）

## 背景

v2 自举片（20 场、4 分 44 秒）看片反馈三条：中间 15 场连续同一版式（file 场景：
左大框 + 右要点栏）；大框里只有两行摘录，九成面积是空的；摘录以源码形式显示
（`**bold**` 星号原样出现），白底高亮条浮在深色面板中央。

诊断出三层根因，都不在「模型不努力」：

1. **类型表没有文本原生场景**。渲染器有 8 种类型，但 `gallery` / `clip` /
   `document` 都吃媒体文件（图片 / 视频 / Office）——纯代码仓库实际可选的只有
   `file`，全片必然 file 连播。「让 agent 自主选择」的前提是菜单里有得选。
2. **密度问题在上游**。digest 的 `excerpts` 契约是单句级（`{ file, text }`），
   写稿模型「摘六行」是无米之炊；密度比 1.5–3 是总量带，两行摘录 + 两条要点就能
   过线，没有单项硬门。
3. **渲染器把散文当代码**。摘录统一走 shiki 源码高亮，shiki 是高亮器不是
   Markdown 渲染器；`github-light` 主题的 `<pre>` 自带白底，与深色主题相抵。

## 决定

按 0001 的分工切三层，每条改动归一层：

- **程序给能力**（渲染器）：版式重做、Markdown 渲染、深色主题、新场景组件；
- **模型做选择**（skill 指引）：挑场景类型、摘多大的块、节拍怎么排；
- **校验器守底线**（check.ts）：行数下限、摘录真实性、版式多样性提醒。

三个工作包，依赖关系决定顺序：

### WP1 · file 场景版式重做 + Markdown 渲染（纯渲染器）

- shiki 换 `github-dark` 并把 `<pre>` 底色并进面板色（transformer 清内联背景）；
- `.md` / `.markdown` 的摘录改走真正的 Markdown 渲染（`marked`，同步、零配置），
  粗体 / 列表 / 行内代码按视频主题出样式——shiki 只留给真代码；
- File 组件：顶部对齐不再垂直居中、面板撑满、字号按行数自适应；摘录带行号槽与
  来源区间标注（新增可选字段 `excerptStart`，摘录首行在源文件中的 1 基行号）；
- 校验器两条新 warning：无素材 file 场景摘录 < 6 行（`excerpt-too-short`）；
  摘录行在源文件里找不到（`excerpt-unverifiable`，拦编造摘录——与拦编造路径
  同一哲学，warning 级因为换行拼接可能误报）；
  **摘录按扫读打折计宽**（实施时的校准修正）：8–12 行的整块摘录在画面上以小字号、
  带高亮呈现，观众扫读锚定而不是逐行精读——密度比里摘录按 1/4 计宽、封顶 100。
  不打折则「标准画面」永远爆密度上界、两行旧摘录反而落在带内，信号正好相反。

### WP2 · 内容密度：digest 升级 + skill 指引

- digest 的 `excerpts` 从单句升级为块级摘录（多行、带起始行号）——写稿模型的
  「合适密度」从富集里选出来，先得有富集；
- skill：「摘六行上下」改为「摘 8–12 行的整块」，与新版式的量匹配。

### WP3 · 场景类型扩展 + 自主选择

- 新增三个**文本原生**场景类型：`concept`（大字论断 + 支撑要点）、`compare`
  （左右两栏对比）、`flow`（步骤条）。不为 terminal 之类加类型——`file` +
  bash 高亮已覆盖；
- 每个新类型过全套：契约与字段白名单、schema、check、plan、组件与测试、skill
  类型表与选择判据、page 同步、示例讲稿；
- 校验器加**多样性提醒**：内容场景里 file 占比超约六成报 warning（只提醒不强制，
  选择权留给模型）；
- skill 选择判据改成「先问内容最好的形态是什么（一段代码 / 一个流程 / 一组对比 /
  一个论断），再选类型」。

## 与 HyperFrames 的取舍对照

HyperFrames（HeyGen 开源，Apache 2.0）验证了同一条工程路线：浏览器逐帧 seek +
FFmpeg、agent-first、skills 分发。但信任模型与我们相反：**它让 agent 直接写自由
HTML，靠 21 个 skills 教模式 + lint 兜底；我们坚持声明式契约 + 校验器闭环**。

坚持契约的理由（写给后人，也回应「为什么不像它那样放手」）：

1. **可校验**：自由 HTML 无法机械地查「路径真实存在」「数字亲手数过」「密度在带
   内」；契约把创作约束成可断言的形状，0004 的四条机械检查才立得住。
2. **密度可控**：版式无限 = 密度不可控；类型化版式让「画面阅读量 / 旁白量」成为
   可量的东西。
3. **逐帧一致好测**：声明式意图 + 渲染器实现曲线，同一份讲稿渲染两次逐帧一致
   是我们已验收的硬指标；自由 HTML 里 agent 引一段 wall-clock 动画就破了。

同时吸收它验证过的两点：**「模板菜单 + agent 按需挑」在 agent 侧走得通**（WP3
正照此做）；**渲染引擎可以替换**——见 `docs/plans/hyperframes-render-engine.md`。

## 验收

每步 `pnpm typecheck` + `pnpm test` + `pnpm run check` 全绿；中间用
`pnpm render <目录> --still <秒>` 静帧目检；**自举片整片重渲放在 WP3 完成后做
一次**，作为最终验收样片。
