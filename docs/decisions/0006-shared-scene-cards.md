# 0006 · 视觉基定浅色编辑风 + 渲染层统一到共享场景卡

日期：2026-10-09　状态：已实施　关联：0001（程序不替模型干活）、0004（两阶段创作与节拍）、0005（版式多样化与密度）、[hyperframes 引擎计划](../plans/hyperframes-render-engine.md)

## 背景

两个事实推着这条决策：

1. **page.html 与成片是两套平行视觉实现，设计投入全在 page 一侧。** page 有三套认真调过的
   预设（素稿的纸白 + 赭红 + 发丝线 + 场景编号），渲染器只有一套硬编码深色 token 与
   React 内联样式组件；0005 每个「page 同步」工作包都要单独记一笔，`samePaletteAsVideo()`
   这个防漂移函数本身就是症状。
2. **色板实验（2026-10-09）量化了「丑」的构成。** 只换 token（深色汇报风 → 素稿浅色），
   视觉盲评 6→7、5.5→7 分：色板是真实提升，但主导缺陷与色板无关——文件面板大面积空腔、
   构图头重脚轻、右侧要点栏悬浮无对齐、字幕条事后贴附、标题与内容缺分隔线。这些结构
   缺陷在 page 侧早已解决，只是没有通往视频的路。证据：`.foldercast/out/palette/`
   （dark-*/light-* 静帧与 compare.html 对照板）。

结论：**问题不是「Remotion 做不出好画面」（Remotion 最终渲染的也是 HTML/CSS），而是
同一份讲稿养着两套视觉实现。** 修法是收敛到一套。

## 决定

### 1. 视频视觉基：浅色编辑风（素稿色板）

`renderer/styles.ts` 的 TOKENS 换成 page 素稿预设的七色，shiki 同步换 `github-light`，
radius 10 / shadow 0（瑞士风靠线不靠影）。`samePaletteAsVideo()` 的配对方从夜幕改为素稿
——夜幕降级为页面独立选项。深底不是删除，是降级：真需要深色成片时作为第三个出口再加。

### 2. 渲染层统一：共享场景卡（scenecard）

新模块 `scripts/scenecard/`：**一份场景卡实现（HTML + CSS）服务两个出口。**

```
script.json ──page/collect.ts──► SceneCard ──┐
                                             ├─► scenecard/render.ts ──► page.html（文档拼装）
script.json ──renderer/plan.ts──► Plan ──────┘                          └─► mp4（Remotion 逐帧）
                    └─ renderer/cards.ts ──► 场景卡 HTML（Node 侧算好，纯数据进 inputProps）
```

- **卡的形态**：视频按 960×540 基准盒排版，`transform: scale(2)` 到 1920×1080——与
  page 的 960px 阅读宽度、15px 正文字号严格 2:1，页面的版式数值原样可用，不需要第二套
  字号阶梯。超出 540 基准高度的内容 `overflow: hidden` 裁掉（密度校验是上游闸门；
  卡片自然高度的机械测量是日后再补的检查）。
- **节拍机制**：卡片 HTML 里的节拍元素带 `data-beat="i"` 与 `data-enter`；CARD_CSS 写成
  消费 CSS 变量（`opacity: var(--b3, 1)` 之类），**缺省值 1**——page 没有时刻概念，全部
  直接可见，零 JS。视频侧由 Remotion 包装组件每帧算 `--bN`（帧号 → 缓动进度，纯函数）
  设在注入容器上，CSS 变量沿 DOM 继承下去。**没有 wall-clock、没有 CSS keyframes**，
  同一帧号同一画面，逐帧一致的判据不变。
- **分工不变**（0001）：契约、校验器、密度检查、节拍-字幕对齐、配音全部不动；模型照旧
  写 `script.json`。变的只是「讲稿 → 像素」的内部路径。
- **字幕条与进度线留在 React 层**（与音轨时序强耦合，且要全局帧号），不进卡片。
- **cover / outro 按媒介分版式**：page 的 hero 带与视频的封面卡内容本就不同（lede vs
  facts），共享的是设计 token 与 CSS，不是同一份标记。八个内容场景类型共享同一份标记，
  仅以 `card--page` / `card--video` 模式类区分布局（如要点栏在 page 是平铺清单、在视频
  是右侧栏）。

### 3. 与 HyperFrames 计划的关系

`data-beat` + 外部驱动变量正是 HyperFrames 的 adapter 形态（`data-start` 时间轴）。场景卡
落地后，「重写 React 场景组件」那一项迁移工作量变成「换一个 seek 驱动器」——本决策是
那条迁移路线的铺轨，不是分叉。

## 接受的成本

- React 场景组件（`scenes/index.ts`）整体删除；`common.ts` 只留转场与入场 hooks。
- `golden.local.json` 画面基线必然失效：这是有意的版式改动，删基线重跑生成新基线。
- 高亮/Markdown 的画面预算仍在 Node 侧（shiki/marked 同步算好进 inputProps），卡片只是
  注入——这一层不动。
- 视频侧卡片高度无机械守卫（无布局引擎回读）：先靠密度闭环兜住，溢出裁切的显式警告
  留给日后（golden 基线 + 目检兜底）。

## 验收

- page：现有渲染测试全绿（标记类名不变），页面输出与改前语义一致。
- 视频：`--still` 静帧目检（对照板）、同帧双渲 sha256 一致、golden 基线重生成。
- `pnpm typecheck` + 相关单测绿；全量 `pnpm test`（含 Chrome 用例）过后再谈提交。

## 落地后发现：一致性判据从字节级改为视觉级

阶段收尾时「整片双渲字节一致」的用例间歇性失败。系统排查（新旧渲染器 A/B 交叉实验、
逐特征消元、每配置十连渲）结论：**与场景卡架构无关**——旧渲染器只把色板换成浅色就
同样漂移；触发条件是浅色主题本身：Chrome 的字形光栅化跨进程存在亚像素噪声，深色
背景时被 JPEG 量化抹平（字节恰好相等，旧判据因此绿了几个版本），浅色背景下过不了
量化（实测：约一成帧数受影响，最小每帧 PSNR **78.3dB**——远超人眼分辨极限，属纯
噪声）。顺带证伪并修正了两个中间假设：场景级 `delayRender` 会让截图时机漂移（已改
为整片开工前一次性预载全部卡片图片）；`premountFor` 不是诱因（保持 1 秒）。

**判据改为：每帧 PSNR ≥ 45dB（字节相等作快速通道）。** 真画面回归（错帧、字幕错位、
图形缺失）会远低于 45dB，防回归能力不变；文案同步改为「逐帧视觉一致」。
