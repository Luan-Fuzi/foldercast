# 0007 · 密钥类文件按文件名排除，判据只做一层

- 状态：已接受
- 日期：2026-10-04
- 决策者：项目作者

## 背景

[ADR 0006](0006-narration-layer-moves-up.md) 决定叙事层可以通读文件内容，因此需要回答：哪些文件不该读。

作者的原始提问指出了这里的逻辑循环：

> 「密钥类文件先保持不读吧，但是这一点很难说。比如什么是密钥类文件？我不读它怎么知道它是密钥类文件？」

**本文的第一版曾决定用三层判据（文件名模式 / 内容签名 / 赋值 + 高熵）来回答。该决定随后被作者否决，本文记录的是否决后的结论。**

作者否决的理由：

> 「你不可能知道用户会把秘密藏在哪个地方。我们管不了用户，那与其这样，还不如我们在一开始就声明：我们不会对你丢进去目录里的东西负责。」

## 决策

**只做一层：按文件名排除。**

1. 密钥类文件名进入**默认排除规则**，不读内容、不进 `manifest[].preview`、不生成素材
2. 被排除的文件**仍进结构树与计数** —— 「这里有个 `.env`」本身有信息量
3. 用户可用 `sources.exclude` / `sources.include` 覆盖
4. **不做内容检测**（不比对密钥格式，不算熵）
5. **在文档与 skill 里明确声明读了什么、不保证什么**，不用免责声明式的措辞

### 默认排除的密钥文件名

```
.env  .env.*  *.env
credentials.json  secrets.json  .netrc
*.pem  *.key  *.p12  *.pfx  *.keystore
id_rsa  id_dsa  id_ecdsa  id_ed25519
.*_key  *_api_key  *_token  *_secret
```

前四项沿用 [Cursor](https://cursor.com/docs/reference/ignore-file.md) 的默认忽略清单口径（它默认只排 `.env*`，其余要用户自己加；我们把安全的那部分直接给成默认值）。

### 声明怎么写

不是「我们不对你目录里的内容负责，自己注意安全」，而是：

> foldercast 会读取目录里的文件内容用于理解，这些内容会进入模型上下文。
> 我们默认排除 `.env`、`credentials.json`、`*.pem` 等密钥文件名，但**这个列表不可能完备** —— 请自行确认目录里没有不该外传的内容。

**区别在于**：前者只说"不负责"，后者说清"我们做到哪一步、从哪一步开始是你的"。用户能据此做决定。

这句话有确定的落点：README 一段 + `foldercast` skill 正文里的明确指令。skill 里那句是运行时生效的约束，不只是文档。

## 理由

### 1. 同类工具没有一家做内容检测

| 工具 | 做法 |
|---|---|
| Cursor | `.cursorignore` 按文件名排除；默认只排 `.env*`。官方原话：「complete protection isn't guaranteed due to LLM unpredictability」；且「terminal and MCP server tools cannot block access」 |
| GitHub Copilot | 内容排除走**路径模式**（fnmatch），不看内容；官方注明 Copilot CLI 与 Agent 模式**不支持**内容排除 |
| Claude Code | **完全不做密钥内容过滤**，走权限架构（sandboxed bash、工作目录边界、dev container），把「Working with sensitive code」列为 User responsibility |

连安全起家的公司都没做，说明这不是"我们没想到"，而是权衡后的共同选择。

### 2. 内容检测的可靠性有实测上限

针对模式匹配密钥扫描器的边界变异研究（[arXiv:2609.02983](https://arxiv.org/abs/2609.02983)，测 Gitleaks 8.21.2 与 TruffleHog 3.82.13）：

- 十种上下文下检测率 ≥ 0.9976，**但当凭据以连字符结尾时掉到 0.5233**
- 五条规则受影响：两条固定数量词的**完全且确定性地失败**；三条可变数量词的**回溯并匹配到被截断的凭据**
- **Gitleaks 有一个已确认的硬编码终止符白名单缺陷，对大多数凭据类型完全漏检**
- TruffleHog 无边界脆弱性，但覆盖率最窄

单篇预印本，不作为定论。但它与"没有一家做"指向同一结论。

### 3. 假信心比没有保护更糟

一个漏掉一半真密钥的检测器，会让用户以为"这个工具有保护"，于是放心地把刚 clone 的、带密钥的目录丢进来。
如果不声明这一点，用户不会知道。

### 4. 第 3 层（熵）还会随机破坏输出

熵判据会拦掉真实代码文件 —— 含示例 token 的教程、test fixture、日志样本。这些被静默跳过时，用户只会觉得"这片子怎么少了点东西"，不会想到是熵判据干的。

### 5. 第 1 层零成本、确定、可预测

文件名匹配不需要读文件、不需要维护正则、不会随凭据格式变化而失效。
「我们排除这些文件名」是**可验证的承诺**；「我们能识别密钥」不是。

## 后果

**正面**：

- 项目根的密钥文件（`.env`、`credentials.json`、`.*_key` 等命名）不会被读。**注**：C6 现在改为复用 DSH 的凭据 seam，项目级密钥用 `.env`；但 `.*_key` 这类旧命名仍在排除清单里，留着也不会被读进模型
- 判决完全确定：同一个目录跑两次，排除的文件集合一致
- 无误报。用户不会遇到"这个文件为什么没出现在视频里"
- 不需要维护密钥格式正则库，也不随各家 API key 格式变化而失效

**负面 —— 必须正视**：

- **硬编码在代码里的密钥会被读。** 一个 `.py` 文件里的 `API_KEY = "sk-..."` 不在排除范围内。这是最常见的真实事故形态，而我们明确不处理它。
- **用户自定义命名的密钥文件会被读。** `.my_secret_stuff` 除非匹配 `*_secret`，否则照读。
- **排除清单是猜测。** 给的是"典型位置"，不是"所有位置"。

**缓解**：

- README 与 skill 都写明这个边界（见上「声明怎么写」），不假装覆盖
- `sources.exclude` 已有，用户可以自行补充；`stats.secrets` 保留一节列出被排除的文件，让用户能确认清单命中了什么

## 已否决的方案

| 方案 | 否决理由 |
|---|---|
| 三层判据（文件名 + 内容签名 + 熵） | 假信心；研究显示模式检测在真实上下文中会成片失效；熵层还会静默误伤正常文件。**本文初版曾采用，作者否决** |
| 只按内容签名检测 | 同上；且必须先读文件头才能判断，与「不读」目标矛盾 |
| 用模型判断哪些文件敏感 | 判断过程正是要把内容送进模型，与目标相反 |
| 用 git 是否跟踪来判断 | 无 git 的目录（R1 的核心场景）完全不适用 |
| 声明免责、不加任何默认排除 | 默认排除零成本，没有理由不做 |
