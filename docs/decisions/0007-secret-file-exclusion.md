# 0007 · 密钥类文件保持不读，判据分三层且必须可审计

- 状态：已接受
- 日期：2026-10-04
- 决策者：项目作者

## 背景

[ADR 0006](0006-narration-layer-moves-up.md) 决定叙事层可以通读文件内容。作者提出一个必须先回答的问题：

> 「密钥类文件先保持不读吧，但是这一点很难说。比如什么是密钥类文件？我不读它怎么知道它是密钥类文件？」

这个问题成立。它指出一个**逻辑上的循环**：任何"按内容判断是否敏感"的规则，都要求先读内容。

但循环只在"读全文"这个前提下才成立。实际约束是：**判据本身需要的信息量，远小于文件内容本身。**

三条事实：

1. **文件名足够判出大部分。** `.env`、`credentials.json`、`id_rsa`、`.mimo_api_key` —— 这些都是**按约定命名**的。不需要读内容就知道该跳过。
2. **素材提取本来就要读文件。** M2 的 `preview` 提取（代码看首块注释、文本看首段、PDF 看首页）已经要求读文件开头。所以"读一小段用于判断"不增加新的 I/O，只增加一个用途。
3. **漏判的代价是不确定的，误判的代价是可修复的。** 把一个普通文件误判为密钥文件，后果是它不出现在素材里——用户在审计记录里看到，一次确认就能放行。漏判一个真密钥，后果是它进了模型上下文。

**判据的目标不是"准确"，是"典型情况不漏，且判断过程可被人复核"。**

## 决策

**密钥类文件在事实层与叙事层都不读内容，只记录"存在且被跳过"。判据分三层，判断结果写入 `stats.secrets` 供审计。**

### 三层判据

按代价从低到高，命中任一即拦截：

| 层 | 判据 | 覆盖什么 | 代价 |
|---|---|---|---|
| 1 | **文件名模式** | 按约定命名的密钥文件 | 零 I/O |
| 2 | **内容签名** | 提交进仓库的密钥（无论叫什么名字） | 读文件头 ≤ 64 KB |
| 3 | **赋值 + 高熵** | 自定义命名的密钥 | 同层 2 |

**层 1 · 文件名模式**（大小写不敏感）：

```
.env  .env.*  credentials.json  .netrc
*.pem  *.key  *.p12  *.pfx  id_rsa  id_ed25519
*_key  *_token  *_secret  *credentials*
```

**层 2 · 内容签名**（已知格式，命中即拦）：

```
sk-[A-Za-z0-9_-]{16,}                      OpenAI 风格
AKIA[0-9A-Z]{16}                            AWS Access Key ID
ghp_[A-Za-z0-9]{20,}                        GitHub token
-----BEGIN [A-Z ]*PRIVATE KEY-----          私钥块
eyJ...eyJ...                                 JWT
```

**层 3 · 赋值 + 高熵**：匹配 `(api_key|token|secret|password)\s*[:=]\s*[值]`，且值长度 ≥ 16、Shannon 熵 > 3.5。

熵判据是层 3 的关键：**它把"引用"和"值"分开。** `api-key: $MIMO_API_KEY` 与 `"api-key": api_key` 的熵都很低，放行；`token = "xUtNIAsnze8LSzov7ze…"` 放行不了。

### 判据在本仓库的实测

对本仓库 33 个文件（设计文档 + 4 个 JSON 预设 + 1 个 Python 脚本）跑三层判据：

| 层 | 命中 |
|---|---|
| 文件名 | 0 |
| 内容签名 | 0 |
| 赋值 + 高熵 | 0 |

而 `docs/rd/TTS-适配调研.md` 里确实存在 `api-key: $MIMO_API_KEY`、`"api-key": api_key` 这类字符串，**未被误判**——它们不含密钥值。

对 4 个构造样本（3 个含真密钥、1 个纯文档）跑同一套判据：

| 样本 | 结果 | 命中层 |
|---|---|---|
| `.env`（含 `OPENAI_API_KEY=sk-proj-…`） | 拦截 | 文件名 + 内容签名 + 赋值+高熵 |
| `.mimo_api_key`（自定义 key 值） | 拦截 | 文件名 |
| `config.py`（`token = "<32 字节随机>"`） | 拦截 | 赋值+高熵 |
| `notes.md`（写 `$MIMO_API_KEY`） | 放行 | — |

**这一组样本上误报 0、漏报 0。样本量太小，不足以说明真实数据的表现。**

### 可审计：判断过程必须落盘

拦截结果写进 `stats.secrets`：

```jsonc
"secrets": {
  "excluded": [
    { "path": ".env",          "reason": "filename",  "match": ".env" },
    { "path": "src/legacy.py", "reason": "entropy",   "match": "api_key" },
    { "path": ".mimo_api_key", "reason": "filename",  "match": "*_key" }
  ],
  "scanned": 33                     // 实际读过头部的文件数
}
```

**这一节是决策的一部分，不是可选项。** 没有它，用户无法知道"有没有被误拦的文件"；有了它，一次确认就能放行。

### 不读的含义

被拦截的文件：

- 不进 `manifest[].preview`
- 不生成素材（不做缩略图、不高亮、不转页）
- 不参与引用依赖图（作为节点存在，但边不展开）
- **仍进结构树与计数**（`stats.totalFiles` 包含它）

最后一条重要：**"这里有个 .env"本身是有信息量的**（说明该项目需要配置），只是不该读它的内容。

## 理由

1. **判据需要的信息量远小于内容。** 层 2/3 只需要文件头 64 KB；层 1 零 I/O。
2. **不引入新的 I/O 通道。** `preview` 提取已经要读文件头，密钥检测复用同一通道。
3. **熵判据解决"引用 vs 值"的歧义。** 这是三层里最容易误判的一层，熵把文档和真值分开了。
4. **审计比准确更现实。** 不可能穷尽所有密钥命名（作者自己也说"这一点很难说"）。能做的是：典型不漏 + 漏了/误了都能看见。

## 后果

**正面**：

- 项目根目录的 `.<provider>_key` 文件（本项目的 [C6 约束](../REQUIREMENTS.md) 推荐的存放方式之一）不会被读进模型
- 误判可恢复：审计记录里有 `reason` 与 `match`，用户能判断是哪个文件、哪条规则
- 不误伤文档：实测 `docs/rd/TTS-适配调研.md` 里的 `api-key:` 示例未被拦截

**负面**：

- **判据不可能完备。** 高熵混淆过的密钥、Base64 编码后的密钥块、熵被稀释的长字符串都会漏。
- **误判会静默地降低视频质量。** 一个含示例 API key 的教程文件会被整份跳过，讲稿里就少了它——而用户可能永远想不起来去看审计记录。
- **熵阈值是拍的。** 3.5 这个值由 4 个样本验证，样本量太小，真实数据里必然要调。

**缓解**：

- `stats.secrets` 在写稿前打印，让用户有机会确认（而非埋在日志里）
- 提供显式覆盖：`[[sources]]` 里允许 `forceRead: ["docs/tutorial.md"]`，把误判文件放回
- 熵阈值写进配置，不硬编码在代码里

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 不检测，全读 | 项目根放 `.<provider>_key` 是本项目推荐的存放方式之一，全读等于把用户密钥送进模型上下文 |
| 只按文件名判断 | 漏掉提交进仓库的密钥（`.py` / `.json` 里硬编码的 key）——这是最常见的真实事故形态 |
| 只按内容判断 | 有 `.env` 这类内容极短、无签名的文件；且必须先读全文才能判断，与目标矛盾 |
| 用模型判断哪些文件敏感 | 判断过程正好要把内容送进模型，与目标相反 |
| 用 git 是否跟踪来判断 | 无 git 的目录（R1 的核心场景）完全不适用 |
