# 0008 · 先做 DSH 插件，推迟独立 CLI

- 状态：已接受
- 日期：2026-10-04
- 决策者：项目作者
- 取代：[ADR 0005](0005-dsh-plugin-shape.md)

## 背景

[ADR 0005](0005-dsh-plugin-shape.md) 定的是「插件是 CLI 的外壳」，并把「独立工具」列为硬需求：

> **独立工具是硬需求。** foldercast 首先是个能单独跑的 CLI（见 ADR 0001）。插件是它的**外壳**，而不是它的宿主。

作者在讨论 LLM 凭据放哪时改变了判断：

> 「我们先专注于做一个 DSH 插件出来，这个插件里面可能包含一些脚本和 skill。我们先不考虑外部调用是怎么样的，先专注于在 DSH 这个工具里面把 workflow 包括我们的验收做好，然后再考虑要不要脱离 DSH 再去做一个东西。」

理由的完整表述：

> 「我们做插件本身，就是希望 DSH 本身有相对完善的 Agent 能力，我们在这个基础上做一点点我们的工作，这样也方便我们把工作做到相对最好。」

**触发这次改变的具体问题**：叙事层（M3）要调用模型，而设计里没有任何位置放 LLM 凭据。原方案要么让 CLI 自己管一套模型凭据（重复配置），要么通过 DSH 调（没有这个接口）。

## 决策

**第一版只做 DSH 插件，不做独立 CLI。插件内含三类东西：工具、skill、脚本。**

```
foldercast 插件（npm 包）
  ├── 工具：注册给模型（薄，起子进程）
  ├── skill：工作流说明 + 「不读哪些文件」的约束
  └── scripts/：analyzer.py、assets.py、render.mjs …
```

**脚本形态选「甲」**：随插件分发的脚本，用 bash 直接调用，**没有 CLI 命令、没有参数解析、没有 `--help`**。

**编排层从 CLI 改成 DSH 主 agent。** 三步管线的驱动者是模型本身：

| 步骤 | 原方案 | 现在 |
|---|---|---|
| ①-1 分析 | `cli analyze` → Python | 主 agent 调 `scripts/analyzer.py` |
| ①-2 写稿 | `cli narrate` → 调模型 API | **主 agent 自己写** |
| ② 视频 | `cli render` → Remotion | 主 agent 调 `scripts/render.mjs` |
| ③ 配音 | `cli voice` → TTS | 主 agent 调 `scripts/voice.py` |

**`packages/cli/` 改名 `packages/plugin/`。** 独立 CLI 不在第一版范围内，是否做以后评估。

## 理由

1. **叙事层的模型凭据问题在这个形态下不存在。** 写稿的模型就是 DSH 主 agent 自己，不需要任何凭据、端点或 provider 配置。原方案里这个洞要么补一套 LLM 配置机制，要么承认 CLI 不能独立完成管线——两条路都不好。

2. **编排逻辑交给 agent 是 DSH 的强项。** 什么时候重跑分析、要不要只渲染不配音、换音色后要不要重新对齐字幕——这些判断用代码写要写一堆分支，交给 agent 是免费的。这直接对上了作者说的「希望 DSH 本身有相对完善的 Agent 能力」。

3. **验收也可以用 agent 做。** 叙事质量没有机器判据（[ROADMAP.md](../ROADMAP.md#5-叙事质量没有指标m3-的最大空白)），但在 DSH 里可以起一个**评审 agent**：给它解读与讲稿，让它判有没有编造、有没有讲错重点。这是原方案里做不到的。

4. **少一层抽象。** 甲形态不需要参数解析、编排层、配置加载、错误分类——那些是给"人用命令行"准备的，而第一版的用户是模型。

5. **从甲升级到乙容易，反过来难。** 以后要做独立 CLI，把脚本收拢到一个命令后面即可；先做 CLI 再拆散，会背上已有的参数与配置约定。

## 后果

**正面**：

- 第一版范围显著变小，能看到东西的时间提前
- 不需要设计 LLM 凭据机制、不需要独立发布 CLI
- 验收、重跑、排障都能用 agent 完成
- 工具/skill/脚本在同一包里，版本天然一致（原方案要处理「插件与 CLI 版本对齐」，见 [INTEGRATION-dsh-plugin.md](../INTEGRATION-dsh-plugin.md) 待办）

**负面 —— 必须正视**：

- **失去 CI 可用性。** 没有 CLI 就没有「一条命令跑完整条管线」，CI 里只能跑到脚本层（分析、素材），编排得自己写。
- **失去不装 DSH 的可用性。** 第一版只能在 DSH 内使用。ADR 0001 说的「独立运行」降级为以后的事。
- **绑定 DSH。** 管线的正确性依赖 DSH 的 agent 行为。若将来要脱离，写稿那一步需要重新设计（因为它是 agent，不是代码）。
- **可测性下降。** 脚本层仍可单元测试，但「主 agent 有没有按 skill 说的做」没有自动化判据。

**缓解**：

- 脚本保持**独立可跑**（stdin/stdout + 参数），这样即使没有 CLI，CI 也能直接调脚本测分析器
- skill 里把工作流写成明确的步骤与检查项，让 agent 的行为尽量可预测、可复核
- 评审 agent 的判据写进 skill，作为验收的一部分
- 若将来做独立 CLI，脚本层不用改，只是加一层命令包装

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 维持 ADR 0005（CLI 为主，插件为壳） | 叙事层的凭据问题无解；且第一版就要负担 CLI 的全部成本 |
| CLI 随插件分发但不独立发布 | 保留了 CLI 的成本（参数、配置、编排）却暂时不享受收益（独立使用） |
| 只做 skill，不做插件 | skill 不能提供新能力（Python、ffmpeg、Remotion 都要工具才能跑），见 [INTEGRATION-dsh-plugin.md](../INTEGRATION-dsh-plugin.md#二什么时候用-skill什么时候用插件) |
| 同时做插件和 CLI | 第一版范围翻倍，且两者要各自维护 |
