# 架构决策记录（ADR）

本目录记录**已定型的、影响面较大的决策**，以及当时为什么那样选。

---

## 为什么要写

代码能说明「做了什么」，说明不了「为什么不是另一种做法」。

当有人（包括三个月后的自己）问「为什么不用 HTML 中间层」「为什么配音放最后」，答案在这里，而不需要重新推导一遍。**这防止同样的弯路走第二遍。**

---

## 什么时候写

**必须写**：

- 改变 [SYSTEM-DESIGN.md](../SYSTEM-DESIGN.md) 里的技术选型
- 改变 [specs/SPEC-pipeline.md](../specs/SPEC-pipeline.md) 的阶段划分或顺序
- 改变 `foldercast.json` 的格式版本
- 推翻 [PRODUCT.md](../PRODUCT.md) 里的任何一条非目标
- 新增顶层目录

**不需要写**：

- 补充实现细节
- 修错别字、加例子、改表述
- 在已定方案内做局部优化

判据：**如果一个新加入的人会问「为什么不那样做」，就值得写。**

---

## 怎么写

### 文件命名

```
NNNN-<kebab-case-标题>.md
```

四位数字，从 `0001` 递增，**不复用、不跳号**。

### 状态

| 状态 | 含义 |
|---|---|
| 提议 | 已写，待讨论 |
| 已接受 | 生效中 |
| 已废弃 | 被后续 ADR 取代。**不删除**，在开头注明取代者 |
| 已拒绝 | 讨论后否决。保留理由 |

### 模板

```markdown
# NNNN · 标题（一句话说清决策）

- 状态：已接受
- 日期：YYYY-MM-DD
- 决策者：

## 背景

什么问题需要决策？有哪些已实测的约束？

## 决策

我们决定做什么。一句话说清。

## 理由

为什么这样选。列事实，不列愿望。

## 后果

**正面**：得到什么。
**负面**：失去什么、背上什么负担。必须写，不写等于没想清楚。
**缓解**：对负面的应对。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| ... | ... |

## 参见

相关 ADR 与文档链接。
```

## 纪律

- 一个 ADR 只记录**一个**决策。两个决策写成两篇。
- **ADR 一旦接受就不修改正文。** 改变主意时写新 ADR 取代它，并在旧的开头加注。
- 「后果」一节必须写负面。只写优点的 ADR 是不合格的。
- 备选方案必须包含**真实考虑过的**选项，不是凑数的稻草人。
