# 管线设计

三步：**文案 → 视频 → 配音**。

本文说明每一步的输入输出、内部职责，以及哪些中间产物是稳定的接口。

---

## 总览

```
目标目录
   │
   │  ① 文案
   ▼
foldercast.json ──────────────┬──────────────┐
   │                          │              │
   │  ② 视频                   │  ③ 配音      │
   ▼                          ▼              │
silent.mp4              配音 mp4 + srt       │
                          durations.json ─────┘（回填，供后续重渲染对齐）
```

---

## ① 文案

**目标**：把「一个目录」变成「一份讲稿」。

分两个子步骤，职责不混：

### ①-1 分析目录（analyze）

纯确定性程序，**不调用模型**。产出 `foldercast.json` 的 `sources` 与 `stats` 部分：

- 遍历目录，生成结构树
- 按类型分类每个文件：代码 / 可编辑文本 / 图片 / 视频 / Office / 音频 / 其他
- 识别角色：README、入口文件、配置、测试、文档、素材、构建产物
- 统计：文件数、类型分布、深度、语言构成

**为什么不让模型做这一步**：目录遍历是确定性工作，模型做会漏、会编、会不稳定。程序做，结果可复现。

### ①-2 写稿（narrate）

调用模型，把分析结果写成讲稿，产出 `foldercast.json` 的 `scenes` 部分：

- 决定讲什么顺序、分几段
- 每段写 `narration`（既是配音文本也是字幕来源）
- 每段选画面类型与引用哪些素材

**模型看到的是分析结果，不是原始目录**。这样 token 可控，且不会因为目录里有敏感文件而把内容送进模型。

### 产物

| 文件 | 说明 |
|---|---|
| `foldercast.json` | 分镜稿。**单一事实来源**，人可读可改，模型可重写 |
| `assets/` | 素材（缩略图、PDF 转图、视频关键帧、语法高亮图） |

`assets/` 是**可重算的缓存**，删了能重建。`foldercast.json` 不是 —— 它是创作产物，重跑会得到不同结果。

---

## ② 视频

**目标**：`foldercast.json` + `assets/` → 静音 mp4。

确定性渲染。同一份分镜 + 同一套素材 → 同一段视频，逐帧可复现。

- 渲染器：Remotion（React 组件 → 无头浏览器逐帧截图 → 编码）
- 样式来源：风格预设的 token（见 [../rd/风格预设系统.md](../rd/风格预设系统.md)）
- **此阶段不产生音频**，场景时长由预估字数决定

**为什么先出静音版**：画面定稿是迭代最频繁的环节。静音渲染快、可反复调，不需要每次调用 TTS。

**为什么不用「先做 HTML 再转视频」**：Remotion 本身就是 HTML 渲染器（无头浏览器逐帧截图）。先做 HTML 再转视频等于渲染两遍、动效写两遍、时序维护两处。Remotion Studio 已经提供浏览器实时预览，不需要自建预览层。

---

## ③ 配音

**目标**：给静音视频配上旁白和字幕。

1. 按场景把 `narration` 送 TTS 合成音频
2. `ffprobe` 实测每段音频真实时长
3. 按标点切分字幕块，按字数把实测时长分配到每块
4. 写出 `durations.json`：`{场景 → 音频路径 + 实测时长 + 字幕块}`
5. 用实测时长重渲染，让画面与配音对齐；字幕烧入

**关键设计：时长以实测音频为准，不以预估字数为准。** 不同 TTS 引擎、不同语速下同一段文字时长差异可达 30%。所以配音必须在画面定稿后跑，且跑完要回填时长重渲染一遍。

### 产物

| 文件 | 说明 |
|---|---|
| `audio/scene-N.{mp3,wav}` | 逐场景音频 |
| `durations.json` | 实测时长 + 字幕块，渲染的时序来源 |
| `out/*.mp4` | 成片 |

---

## 为什么配音放最后

| 顺序 | 改一次讲稿的代价 |
|---|---|
| 文案 → 视频 → 配音（本方案） | 改稿 → 重跑写稿 → 重渲染静音 → 重新配音。每一步都可单独跳过 |
| 文案 → 配音 → 视频 | 改稿必须重新调用 TTS 才能看画面，且画面时长被音频锁死，调版式要重配音 |

另外，配音是**唯一有外部依赖和成本**的阶段（API 调用、网络、配额）。把它放最后，意味着一整天的画面迭代不消耗任何 TTS 配额。

---

## 可重跑边界

| 改动 | 需要重跑 |
|---|---|
| 改文字措辞 | ①-2 写稿（或手改 json）→ ② → ③ |
| 换风格预设 | ② → ③ |
| 换 TTS 音色 | 仅 ③ |
| 调整场景顺序 | ② → ③ |
| 目录新增文件 | ①-1 分析 → ①-2 写稿 → ② → ③ |
| 只想预览画面 | 仅 ②（静音，最快） |

## 多个视频

一个目录可以出多个视频：一份总览 + N 份分组深挖。

它们**共用同一份分析结果与素材**，只是 `scenes` 不同：

```
analyze（一次）
   ├─ overview/foldercast.json   → 总览视频
   ├─ module-a/foldercast.json   → A 模块深挖
   └─ module-b/foldercast.json   → B 模块深挖
```

这是把「分析」与「写稿」拆开的直接收益。

### 为什么这不是"可选功能"，而是必需

实测 `/Users/scliang/work`（见下节）后确认：**很多目录本身就是「项目的容器」，而不是一个项目。**

```
workspace/           ← 没有 README，没有入口，纯粹是容器
  ├── project-a/     ← 有自己的 README、代码、素材
  ├── project-b/     ← 有自己的 README
  └── docs/          ← 纯资料
```

对这类目录，**出一个视频是错的** —— 一份讲稿无法既讲清工作区全貌，又讲清每个项目。正确产物是：

- 1 个总览视频：「这个工作区里有 12 个项目，分别是什么」
- N 个项目视频：「项目 A 是什么，怎么组织的」

**所以「多个视频」是容器型目录的唯一正确形态，不是锦上添花。** M3（写稿）必须包含「切分」这一动作，而不只是「写一份稿」。

### 反过来说：单项目目录

对 `foldercast/` 这种单一项目，默认只出一个视频。切分按需触发：

- 目录是容器（顶层无 README 且子目录各自有 README）→ 倾向切分
- 目录是项目（顶层有 README）→ 单个视频，除非用户显式要求拆分
